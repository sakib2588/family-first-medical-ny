# U00. How to use this playbook

Status: draft | Owner task: T7 | Updated: 2026-10-30 | Scope: universal

## Purpose
This module tells Claude Code and a freelancer which files to read, in what order, what binds and what is only advice, and how the client record selects overlays. It is read first in every session, for every client type; trades is one overlay among many, never the default.

## Anti-patterns
- Starting from the last client's site and swapping names. Every client starts from its own record and overlays (U00.1, U00.4).
- Treating a call-first hero or a sticky call bar as universal. They belong to `local-trades` only (U00.7); location pages follow U06.3 for every client.
- Filling an empty field with a "plausible" value so the layout looks complete. The block is omitted instead (U00.10).
- Fixing a wrong phone number in a component instead of in the record; the next rebuild restores the error (U00.11).
- Reading an overlay's stricter rule as a reason to drop a universal rule for every client. Overrides are per client and logged (U00.8).
- Telling a client a page "meets" a law. Legal rows go to counsel (U00.14).

## Checklist
- [ ] Session reading order followed; files read are listed in the session notes (U00.1).
- [ ] `archetype`, `model` and `jurisdictions` hold valid slugs and each overlay file exists; the vertical overlay is not `Status: planned`; each planned jurisdiction or model overlay has its counsel questions on the counsel list and blocks S6 until counsel review or an owner waiver is recorded (U00.4, U00.5, U00.6, U00.7).
- [ ] Conditional rows (`When <record key> includes <value>:`) checked against the record; rows with no condition applied to every client (U00.18, U00.19).
- [ ] Every override of a universal rule is in the decisions log (U00.8).
- [ ] Layers merged in the step 4 order; compliance rows from all layers in one list; conflicts sent to the owner and counsel (U00.9).
- [ ] Fact scan: every business fact on built pages maps to a record field with provenance; no placeholders (U00.10, U00.11).
- [ ] Production build used a locked record (U00.12).
- [ ] No legal conclusion in any output; counsel list current (U00.14).
- [ ] Decisions log and vault log updated (U00.17).

## How an AI builder uses this
Overlay decision tree, run after intake and again whenever the record changes:

1. Read `archetype`. A hybrid or unknown client (two client types, or none that fits) stops the builder, which asks the owner. If null or not one of the vertical slugs (local-trades, restaurants, legal-accounting, medical-wellness, real-estate, ecommerce, saas-b2b, portfolios-creatives, nonprofits, education-courses, events-venues, coaches-personal-brands, manufacturers-industrial, local-retail-salons-fitness, regulated-finance), stop and ask. Otherwise load `playbook/overlays/vertical/<archetype>.md`.
2. For each value in `model` (lead-gen, microsite, ecommerce, subscription, booking, donations, ticketing), load `playbook/overlays/model/<value>.md`. An empty list stops the build: every site has at least one way to convert (see U03, U08).
3. For each value in `jurisdictions` (us-federal, new-york, nyc, california, eu-eea, uk), load `playbook/overlays/jurisdiction/<value>.md`. A child without its parent fails U00.6. A place not on this list stops the build and becomes a counsel question.
4. Merge spec (the only one; STRUCTURE.md points here). Apply in this order: universal modules, then jurisdiction overlays (add legal rows, never remove one), then model overlays (add conversion, tracking and legal rows), then the vertical overlay. (a) The vertical overlay wins over the universal modules and the model overlays on form fields, trust signals, UX patterns and schema types for that client, and over the universal modules on the page set (its Drops may remove U06 skeleton pages, its Adds are taken). (b) Compliance rows only add up, from every layer and from every conditional row that holds (U00.9, U00.18, U00.19). (c) Between overlays, page set = the U06 skeleton plus the union of every overlay's Adds, minus every overlay's Drops; an Add in one overlay that names a page another overlay Drops stops the builder, which asks the owner; the only exception is (f). (d) The primary conversion block comes from `goals.primary` (see U08); overlays constrain the block, they do not pick a second primary. (e) Every override is logged by the overlay rule id (U00.8). (f) When `model` includes `microsite` and `archetype` is `local-trades` (a referral microsite for a trades business is allowed): the microsite overlay's Page-set Drops and its list of what is never shown as the site's own win over the local-trades Adds and Trust signals (no license, insured or contractor-looking pages); local-trades rows that require the contractor's own license, insurance or address display (local-trades.14, .15, .22, .24) do not render as the site's own: each becomes a counsel item in `legal.counsel_items` (does the duty reach a referral site, and must it show the receiving business's details?) and S6 waits for counsel; the receiving business's license is shown only per microsite Trust signal 2; local-trades supplies only its content rows (topics, safety lines, schema exclusions); each such precedence is logged per U00.8; referral licensing, per-job fees, review reuse, markup and the no-license-display rule stay owner decisions, with counsel. (g) When two model overlays conflict on a claim or trust rule, the more restrictive rule wins (with `microsite` and `lead-gen`: the microsite Trust signals and its "never" list win over lead-gen Trust signals 2 and 3; lead-gen supplies capture, routing, ledger, tracking and its compliance rows); each precedence is logged by rule id (U00.8). Red lines and gates sit above every layer (U00.2).

Inputs: `site.yaml`, the decisions log, STRUCTURE.md, the selected overlays. Output: the merged per-client rule and compliance list, written to the decisions log before design starts (see U02 for intake, U20 for the legal list). The builder must refuse to render a fact that is not in the record, to pick an overlay by guess, to waive a red line, and to state any legal conclusion.

## Open questions
- Which vertical overlays are reviewed next after `local-trades` (owner).
- Whether jurisdictions beyond the six listed (other US states, Canada, Australia) are taken at all, and on what counsel terms (owner, counsel).
- Hybrid clients (a restaurant with a shop, a venue with a restaurant): today they stop the builder (step 1); whether a second archetype key is added is an owner decision.
- Model stubs: booking, donations, ecommerce, subscription and ticketing are `planned`; under U00.7 such clients build to staging but cannot launch until counsel review or an owner waiver is recorded; whether the owner sells these client types before the overlays are drafted is an owner decision.
- "Visit" and information sites (a museum, a venue, a visit-only restaurant) have no fitting model slug; whether a model such as `brochure` is added, or lead-gen states that `goals.primary: visit` skips its ledger rows, is an owner decision.
- Known gaps with no module (owner decisions, no new module this round): platform and CMS choice, multi-location sites, content and media migration at cutover, staging access control (the Google block-indexing page, opened 2026-10-30, describes noindex but does not say how to protect staging, so no rule is written).
- How a post-launch fact edit (hours, prices) re-locks the record: proposed `status: in-review`, approved by the named approver, locked again before deploy (owner).
