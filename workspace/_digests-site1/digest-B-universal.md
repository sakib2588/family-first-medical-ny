## 1. END-TO-END PROCESS (stages, gates, sign-offs)

Order of modules in a real engagement:
Pre-call screen -> stop list -> U01 scope/agreement (S0) -> intake Q1-Q12 + live interview (U02) -> **K0 gate** -> brief: goals/KPIs (U03) + audience/brand (U04) = **S1** -> proof inventory (U05) -> site plan: sitemap, page specs, content matrix, conversion paths, event map (U06, U08, U19) = **S2** -> design directions, lock, tokens (U09-U15) = **S3** -> copy + facts, record locked (U07, U20 counsel rows) = **S4** -> build + QA matrix on staging (U16-U21, U23) = **S5** -> launch card, rollback, redirects, DNS = **S6** -> T+7 / T+30 -> handoff pack = **S7** -> T+90 under care plan.

Sign-offs (kit/signoff-log.md). One NAMED approver per point (set at K0, U01.10) plus tie-breaker; approver sees the exact version via link; spoken yes confirmed in writing same day; builder never signs for client; change after a sign-off = change request (CR-n), logged, re-signed if it alters approved content; dates YYYY-MM-DD; decision = approved / approved with changes / rejected; no point skipped (N/A needs reason + initials).
| S | What approver sees | Who |
|---|---|---|
| S0 | Scope (in/out), deliverables, page set, timeline, assumptions, review rounds, change route, agreement (prices in agreement only) | client decision-maker + signatory (U01) |
| S1 | Brief: positioning, audience + top tasks, voice, ONE primary conversion, KPIs (baseline/target/date/source) | client approver (U03, U04) |
| S2 | Sitemap, page specs, content matrix, conversion paths, event map (names primary-conversion event) | client approver (U06, U08, U19). After S2 a new page = CR |
| S3 | 2-3 concept directions, one locked with tokens (color/type/spacing) + key templates at phone + desktop; contrast + font licenses checked | client approver (U09). After S3 palette/type change = CR |
| S4 | Final copy for every page, `site.yaml` with provenance, proof library, rights log; counsel signs flagged legal/regulated rows | client approver + counsel (U05, U07, U20). Record becomes `status: locked` |
| S5 | Staging link + QA matrix (content, function, a11y, perf, SEO, legal pages, devices), known defects | OUR tester (NOT builder) signs first, then client approver (U23). After S5 only defect fixes |
| S6 | Launch card, redirect map, DNS plan, rollback plan, go-live checks; every planned overlay has counsel review or owner waiver; every "must" legal row + every `unverified` legal row + `legal.counsel_items` has recorded counsel decision (U23.13) | client approver |
| S7 | Handoff pack incl. T+7/T+30 results, ownership transfer account by account | client approver (+ signatory for transfer) (U24) |

## 3. INTAKE QUESTIONNAIRE (kit/intake-questionnaire.md) AND WHAT EACH Q DECIDES

Method: written form (facts) + live interview (meaning, ONE question at a time, restate, one follow-up, close topic after two empty follow-ups; ask why on any value word; for generic answers ("modern and clean", "everyone", "great service") demand one concrete example/story/number, U02.7). Every answer logged with source, who, channel, date under `provenance:`. Null means omitted. Several owners: interview each alone first. NEVER skip Q2 (primary conversion), Q9 (legal triggers), Q11 (decision makers). Short path (one page/brochure/microsite): Q1-Q4, Q6 (logo/colors/fonts, 3 words), Q7-Q11, Q12.1-12.2, Q5 only reference sites. Full path: Q1-Q12, several sessions, one brand topic each.

**Pre-call screen (15 min, alone, public sources; write to site.yaml `status: draft` with source/date)**: archetype guess (hybrid => owner); model guess; operating places + signs of EU/UK/CA visitors; regulated work visible (flag counsel before scoping); transactions today/planned; current site snapshot (first phone screen, is main action visible, broken pages/forms); listings/profiles copy NAP exactly with date; visible proof (what exists, not how good); real-business check; source mismatches (two names/phones/old address); appetite fit; can the contact decide; stop flags; 3-5 opening questions.

**Stop/decline list (any yes halts; log flag + outcome):** unverifiable reviews/testimonials/staff/addresses/licenses/awards/numbers or AI people shown as real => DECLINE (red line); guaranteed ranking/traffic/leads/revenue as condition => explain, decline if persists; no real business => decline; **regulated business (medicine, dentistry, therapy etc.) with no counsel to review => PAUSE until named counsel agrees**; no single approver/tie-break => pause; client shares passwords not invitations or third party holds domain/listing/hosting and refuses transfer => pause, never accept password; client supplies nothing and says "just write something" => smaller site or decline; red-line tactics (hidden text, doorway pages, bought links, bots, fake listings, fake independent sites) => decline; wants to imitate another business or claim someone else's license/address/affiliation => decline; site must collect **health**, financial, children's or card data and scope cannot cover safeguards => PAUSE and rescope or refer, counsel; impossible deadline => smaller first release; conflicts with existing client agreement => decline.

## 5. GOALS, AUDIENCE, PROOF, IA, CONTENT (U03-U07)

**U03 Goals/metrics.** .1 `goals.primary` = exactly one visitor action, verb + object ("engagement/awareness" fails). .2 secondaries in `goals.secondary`, none with equal visual weight on same screen. .3 each goal -> signal + metric. .4 each KPI has metric, baseline, target, target_date, source (+ baseline_is_guess) or it is not reported. .5 guessed baseline labelled "estimate"; new site baseline null, target set after first full reporting period. .6 targets from client's own baseline/capacity, NOT industry averages/vendor benchmarks. .7 targets are goals not guarantees. .8 every page spec names the action it serves (primary or one secondary) or is cut/justified. .9 each conversion = one named event, defined pre-build, triggered on CONFIRMED success not click. .10 GA4: primary conversion marked key event. .11 off-site conversions (phone call, walk-in, third-party booking widget) need counting method + source system; otherwise "unmeasured", not estimated. .12 every KPI source accessible by invitation, confirmed at K0, else KPI removed. .13 consent-gated KPIs labelled "partial". .14 page views/sessions/time-on-page only as signals tied to a goal. .15 review cadence T+7/T+30/T+90 (owner policy), each review records what will change. .16 goals/KPIs/measurement plan approved at S1; later primary change = CR.

## 12. PER-PAGE SPEC METHOD (what exists, and what each page type needs)

There is NO single per-page template file. The "page spec" is the composite of these rules; a page is not drafted/designed/built until each item below is filled:
1. `pages[]` entry in site.yaml (U06): slug, type, job, primary_action, template, overlay_source, writer, approver, status (requested/draft/edited/client review/approved/published).
2. U07.1 page job statement: audience, top task (U04), the ONE action (U03.8), proof items used (U05), owner.
3. U08.1 pattern block named; fields from block minimum; confirmation page and event (U08.10, U19.1).
4. U10.1 first-look order for the template (+ blur test) and U10.2 first-phone-view contents.
5. U06.7/.8 template section order and collection fields (type, required, owner, source); null fields render nothing.
6. U18.1 one primary search query/task; title, meta description, one H1, canonical, schema type (U18.2-.10).
7. U04.16 cites the brief section it implements.
8. Content matrix row (kit/content-request.md): Page | Page type | Job | Primary action | Writer (client / us / specialist) | Source (interview / existing page / record) | Proof needed (proof ids) | Word target (set by job, not fixed length) | Due | Status (requested, draft, edited, client review, approved, published) | Approver. Writer options: client writes; we draft from interview + record; reuse existing page; specialist (counsel/translator).
9. U15.15 states and screenshots for components on the page; U14 motion inventory; U13 image slots with source type + alt; U17 budget on template.
10. Review: two rounds of client comments default, one combined comment set from the approver; S2 approves page specs; S4 approves final copy; page added after S2 = CR.
Suggested "grill" order per page: job/action -> audience/task -> proof available (fact+provenance+consent) -> first-look/first phone view -> content sections + facts -> conversion block + destinations -> SEO query/schema -> design (tokens, imagery rights, motion) -> a11y/perf/legal -> tests.

Page types in content-request.md (what the client provides):
- Home: first-phone-screen understanding (what offered, for whom, where, the one action); 2-3 strongest proof pieces; which top tasks need direct links.
- About/story: how/why started in own words; people + consent for names/photos; values with one real example each.
- Offer pages (service/product/program/practice area/plan): what it is, who for and NOT for; how it works step by step; included/not included; how long + what changes it; price shown per Q4.4 from client price list only; which customer questions it answers; offer-specific proof.
- Collection/listing pages: grouping, filters/sort, who updates data from which source file.
- Location/area pages: ONLY with unique local proof per place; else one combined page.
- Case studies/portfolio: client sign-off, problem, action, result with source + period.
- Team/people: name, role, credentials, real photo, written consent (and credentials checkable with issuer).
- Pricing/plans: exact terms, fees, renewal/cancel rules in counsel-approved wording.
- FAQ: real customer questions, approved answers, short, factual, matches record; written for people not rich results.
- Contact/booking/checkout/donation/application: required fields and why; two destinations + who answers; confirmation message/email text; failure fallback; after-hours message + honest response time.
- Blog/news/resources: who writes, how often, which real question each post answers, who reviews before live.
- Events/schedules/menus: editable source file + updater.
- Legal/policy pages: privacy notice, terms, cookie notice, accessibility statement, refund/cancellation policy, field-required notices: who supplies, who reviews (counsel). We format and place legal text; we don't write it as legal advice.
- Careers (optional), System pages (thank-you/confirmation, not-found, maintenance), Translated pages.
- Utility pages required by U06.9: 404, confirmation per conversion, service-unavailable where transactions.
Clinic-specific pages from medical-wellness overlay: Services/treatments (one each), Providers (one bio each), Locations and hours, Insurance and pricing, New patients (forms/what to bring), Patient portal link (separate from new-patient path), Telehealth if offered, Notice of privacy practices, good-faith-estimate notice, nondiscrimination/language-assistance notice where applicable. Dropped: before/after gallery; unreviewed health-claims blog. Plus lead-gen overlay adds: thank-you page per form, privacy page linked beside every form. Location pages follow U06.3.
