## 0. The 12 rules that matter most (cross-cutting)

1. One source of truth (`business.yaml`/`site.yaml`); a fact not in it does not appear (5.1). Null = omitted, no hedge. Provenance on every fact. [X]
2. Every lead goes to TWO independent destinations, test-proven (14.5, U08.12). [X]
3. Form fails closed: success is shown ONLY after the row is stored; failure shows the phone and keeps typed values (14.4 step 9, U08.11). [X]
4. Never delete a flagged lead; spam goes to a review queue a human reads daily (14.9). [X]
5. A quiet fortnight is a fault until proven otherwise (continuity alert 16.3). [X]
6. The landing page must convert alone: the page Google sends people to is usually the entire site visit (R2 A1, 7.1). [X]
7. One primary action per screen; no stack of buttons (R2 A4, 10.4, U08.2). [X]
8. Trust facts before the ask; real or absent, never invented (10.5, 12.7, red lines 26.1). [X]
9. Test the deployed preview, not the local build; the tester is not the builder (22.1). [X]
10. Client owns every asset (domain, listing, numbers, analytics); never hold hostage (26.1 #4, H.12.7). [X]
11. Never promise rank/lead count/revenue (26.1 #8). [X]
12. Dated snapshot before any change; one change at a time, logged; never promise a recovery date (H, three recurring rules). [X]

## 1. CONVERSION SYSTEM: capture, routing, forms, tracking, follow-up, proof

### 1.1 Capture checklist (14.1, C.2): each item pass/fail BEFORE any traffic [X]
- Every phone number is a `tel:` link built from the record's E.164 value; dials on a real phone. Display formatted number as TEXT, never an image (14.3).
- Every call surface attributed or counted (site, ads, directories by source; listing calls from Google's performance report).
- Lead form delivers to TWO destinations; a test submission reaches both inside 2 minutes (ours).
- Alert reaches a named human by TWO channels (14.6).
- Spam control on and verified on the SERVER (14.4).
- Failure state shows the phone number and keeps what the visitor typed.
- Every form stored in D1 and synced to the ledger; daily reconcile finds gaps.
- Thank-you page fires the conversion event exactly once.
- Synthetic test submission runs daily and alerts on failure (14.8).
- After-hours path exists, is written down, and was tested (16.4).

### 1.2 Contact surfaces (14.2) [X, medical adaptation on forms]
Phone from site (tracking number/event + call log); phone from Google listing (listing performance counts; GBP call history and chat ended 31 Jul 2024); contact form (POST to endpoint; server records, alerts, returns success only after storing); text (vendor or manual); LSA/ads (platform + vendor); email (manual/forwarding rule); walk-ins/referrals (client logs them at monthly tag review 23.5).

### 1.3 Click-to-call (14.3, 10.3, 10.10) [X]
- `tel:+1...` E.164 in built HTML. Number in header, hero, mobile sticky bar, footer, contact page. On desktop show number as text plus button.
- Past bug: a phone link that went to the home page instead of dialing (R2 A2); caught by `check-ctas` guard and click-through test.
- `phone_click` event with `placement` param (header, hero, sticky, footer, contact) via a tiny inline listener, NOT a tag manager.
- Call button >= 48 px tall, full width on mobile, 8 px gaps (clears WCAG 2.2 AA 24 px, web.dev 48 px, Apple 44 pt).
- Sticky mobile call bar: ship + instrument + A/B before claiming a lift (no rigorous test exists; +20% to +250% claims are blogs). Do not cover content or the submit button (10.6, U08.3: shows only when no other primary action/form/footer is visible). 0 of 8 Queens HVAC competitors had one (R9).

### 1.4 The form backend (14.4): "every public form fails closed; every form lead has exactly one system of record" [X; medical = see 1.12]
Flow: browser POST JSON to `/api/lead` same site -> Worker guard -> store row in D1 (system of record) -> background: alert email, optional ack, n8n sync -> success ONLY if row stored.

Guard order (fixed after REVIEW-3):
1. `Origin` must match site; POST without it rejected.
2. Body cap 16 KB; expected content type only.
3. Signed synthetic test (if signature header present): HMAC over `timestamp.body`, timestamp within 2 min, id must be `synthetic-`+fresh (becomes row id; PK refuses replay). Bad signature = 403. Skips ONLY Turnstile; stored `is_test=true`; alerts Owner only, never the client.
4. Rate limit 5/min/client, counting EVERY request incl. rejected (record attempt first, then count); IPv6 keyed on /64; plus Cloudflare edge rule (Free plan: 1 IP-only rule, 10 s window); disable button in flight.
5. Honeypot (unremarkable name, not autofillable): if filled, return 200 with a real-looking id, STORE a row `status=spam, reason=honeypot` keeping submitted data (capped), send NO alert; goes to review queue (14.9).
6. Field validation with field-level 400s BEFORE Turnstile (tokens are single-use; a ZIP typo must not burn the token). Name, phone (E.164), service from allowed list, ZIP, optional email (strict, lowercased), optional message. Reject control/zero-width/bidi chars in single-line fields, strip from message (name goes in email subject). `page` must be a path starting with exactly one slash.
7. Turnstile verified server-side (siteverify; check hostname and action); widget alone protects nothing; token valid 300 s, single-use; browser resets widget after any failed response; secret missing = 503 (never fail open).
8. De-dupe: same phone within 10 min returns first lead's id, no second row/alert (REVIEW-4 M2 says refine: only dedupe when service+zip+message match; else store and alert "second request from same number").
9. Store, then respond. DB down = JSON 503 telling visitor to call.

Row fields: `received_at, source, page, fields, status, is_test, notified_at, email_error, synced_at, sync_error, retries`. Failure must be visible, not silent.

Alert retry (REVIEW-3 H1 / REVIEW-4 H1 fixes): cron every 15 min; retry real leads with no alert after 5 min; re-copy to n8n (idempotent on row id); email Owner on first and last failed retry; purge attempts after 1 day, spam after 30 days. REVIEW-4: do NOT cap retries by count (stop-at-3 abandons leads forever); persist `owner_alerted_at`; give Owner a SECOND channel that does not depend on the failing provider; mandatory external dead-man check on the synthetic test.

Ack email to the visitor: OFF by default (anyone can type another person's address -> spam relay on the agency's authenticated domain; REVIEW-3 M2). Enable per client only with per-address daily cap. Text ack needs 14.7 conditions. [M: for a medical form an ack email must not echo clinical details.]

Never put the n8n webhook URL in browser JS; Worker calls n8n with header secret.

API tests before launch (14.4): valid saves row+alert; bad email 400 and does not spend Turnstile; 25 parallel posts store at most 5; honeypot stores spam row, no alert; name with line break refused; alert-provider failure retried by cron and Owner told; failing Turnstile (always-fail test secret) 403; POST without Origin rejected; signed synthetic stored with `is_test` and Owner-only alert; bad-sig/old-timestamp/repeated-id synthetic rejected.

### 1.5 Alerts that arrive (14.6) [X]
- Send from an authenticated domain (SPF, DKIM, DMARC p=none then tighten); Gmail requires SPF/DKIM from all senders; unauthenticated mail from a new domain lands in spam = the real failure. Never send from the client's Gmail.
- Two channels: email + SMS/push (about $4-6/client/month on Twilio; vendor prices).
- Provider limits: a free tier with 100/day can be exhausted by ~50 junk leads (REVIEW-3 H1); budget the paid tier.
- Alert content: name, tap-to-call phone, service, ZIP, message, source, time, one-tap call-back. [M: minimise PHI in an email/SMS alert; see 1.12.]

### 1.6 Text to leads (14.7, 26.4) [X; medical = counsel]
Texting a lead needs: EIN-registered business, live privacy + SMS-terms pages, A2P 10DLC brand+campaign registration, separate UNCHECKED consent box (U08.15 no pre-checked boxes). Honor STOP and any plain "don't text me". Send marketing/follow-up texts 9 a.m.-8 p.m. recipient time (ours; 47 CFR quiet hours 8-9; NY GBL 399-z reportedly same, counsel). FCC one-to-one consent rule vacated 24 Jan 2025; still collect consent and keep proof. AI-voice callbacks are outbound artificial-voice calls needing prior express consent (FCC 24-17); an inbound AI answering a caller is not "initiating" (our reading; counsel). Chat widgets: OFF by default (speed cost; GBP chat ended).

### 1.7 Spam control without eating real leads (14.9) [X]
Never delete a flagged lead -> review queue checked daily; log everything incl. rejected posts with reason; measure capture rate (client-reported contacts minus ledger); tighten gradually: honeypot -> Turnstile -> rate limit -> content rules LAST. Honeypot autofill can trip real visitors (REVIEW-3 M4, REVIEW-4 L3): rename to unguessable `hp_`+random, add 2-second time trap, daily digest of spam rows with "this is real" link, include the visible phone in the success response for honeypot hits.

### 1.8 Call tracking & attribution (15) [X, with a medical privacy caveat]
- Events (15.1): `phone_click` = intent (not a call); Call = vendor log (connected, duration, source); `generate_lead` = thank-you page after confirmed server success; `directions_click` = walk-in intent (storefronts); listing calls/website clicks/direction requests = GBP performance (aggregate).
- Fire `generate_lead` only on the thank-you page (7.5); GA4 `form_submit` unreliable on AJAX forms (our knowledge). REVIEW-3 L11: `generate_lead` can be forced via `sessionStorage.lead_ok`, so conversion counts are not evidence.
- Vendors (checked 24 Oct 2026; re-verify): CallRail $50/mo (5 numbers, 250 min; form tracking from $95); WhatConverts $30 = ONE account (agency/unlimited accounts from $500); CTM $79; CallScaler $65. Cost per client ~$35-75/mo. First 1-3 clients: one account per client billed to the client (client owns number).
- Number architecture (15.3) - live conflict, default PR9: listing = real number PRIMARY, tracking number ADDITIONAL (Google never endorses tracking-primary; max 1 primary + 2 additional); site = real number in HTML/schema/footer/contact; DNI swaps visible tap-to-call numbers for human sessions; ads use Google Ads call assets/forwarding number; citations carry the same primary number character for character. Test the alternative on ONE client only with before/after grid. Port check at intake (inherited prior-agency numbers).
- REVIEW-2 HIGH 1: this default means organic-site and listing calls never touch the tracking vendor -> client-facing promises like "you will see every lead and where it came from" are dishonest. Say "tracked calls and forms; listing calls counted from Google's report, not traced" (15.8).
- GA4/Search Console owned by the client with us as users; 12-month baseline pulled at onboarding; Search Console omits map-pack clicks and AI Overview traffic; listing UTM `?utm_source=google&utm_medium=organic&utm_campaign=gbp_listing` default-on, test one client both ways (R2 M3/X2).
- AI traffic: GA4 channel regex is a floor; add "How did you hear about us?" with AI options to form and call intake.
- Recording OFF by default until consent confirmed per state (15.6): NY one-party; NJ one-party (RCFP 2020); CT civil statute all-party/recorded warning (RCFP 2019; statute not fetched). Design rule (ours): treat every call as all-party; play notice ("may be recorded and handled by an automated assistant"); one lawyer's read before launch. With recording off, evidence = call-log metadata + human tag. Retention per field: salted hash for dedupe; readable number truncated to area code after 90 days (REVIEW-2 #12 notes this destroys dispute evidence - decide retention in agreement). [M: call recording of patient calls = PHI; counsel + BAA, likely keep OFF.]
- Call -> ledger row (15.7): vendor webhook/n8n poll writes time, source, tracking number, caller, duration, recording link, answered/missed, `status=new`; a person tags **lead / marketing / junk**; keep tags (dispute evidence); weekly report counts only tagged leads.

### 1.9 Speed to lead & routing (16) [X]
- "Respond within 5 minutes" is a sound operating target, NOT a measured lift. The "21x" is misquoted everywhere: original InsideSales/MIT 2007 study = odds of QUALIFYING a lead called in 5 min vs 30 min, B2B web leads called by sales reps, six companies, ~15,000 leads; 100x is CONTACT odds; says nothing on close ratios or home services; not HBR. HBR 2011 (1.25M leads; ~7x within the hour vs next hour) known only via secondary summaries. NEVER put 21x in a proposal (AR6).
- Home-service vendor data (Invoca July 2026, vendor claim, sample undisclosed): human answered 52% of inbound home-services calls (HVAC 34%, construction 32%, plumbing 74%); 38% of answered calls are leads; 45% of leads convert on the call; 55% of businesses never ask the caller to book. Use only as a prompt to measure the client's OWN numbers. Podium "78% go with first responder" and "4x if under 5 min" = vendor/L-M.
- Targets (ours, 16.2): call in hours rings owner/dispatcher 15-20 s then rolls to answering layer, answered every time; missed call in hours = 2-channel alert within 60 s, callback within 5 min; form in hours = alert within 2 min, human contact within 5 min; form/call after hours = alert at once, emergency path rings owner, non-emergency contacted by 9 a.m. next business day; emergency = phone the lead, do not text.
- Routing table (16.3): answered call -> client; missed call (hours) -> answering layer then ledger, SMS+email, flagged `missed`; form (hours) -> ledger+client, 2 min; form after-hours -> queue, alert to named on-call person (OQ3), morning digest; emergency keyword in form -> hot, phone/priority push to owner within 2 min; spam -> review queue, daily digest; out-of-area -> ledger `out of area`, polite decline by CLIENT; no contact event for 14 days (tests excluded) in a normally-active business -> alert Owner, check listing/phone/form/site (24.7).
- After-hours options (16.4): owner's phone rolled over (free, best close, burns owner); answering service ($30-40/mo basic practitioner claim; human-staffed Ruby $250+); AI voice agent ($0.08-0.13/min on Vapi/Retell; $79-150/mo packaged); voicemail only (callers hang up; figures unsourced). Escalate if rolling missed-call rate > 20% for 3 weeks (coach figure; target ours).
- AI voice agent (16.5): disclosure + recording notice up front; "say 'person' any time"; business hours ring owner first; HARD-CODED emergency path (client approves wording in writing; no source supplies a script); one question at a time; NEVER quote price/timeline; callback promise matches reality (course template's "within 72 hours" is too slow for urgent work, R3 C10); log transcript/outcome; review failures daily for the first month; per-client kill switch to a human; test accents/noise/mixed languages. NY GBL 396-b (eff. 2026-06-09) covers ADS with synthetic performers, not clearly inbound assistants - disclose anyway. [M: an AI agent triaging symptoms = serious clinical/legal risk; MED-NEW: restrict to scheduling/message-taking, hard-code "if this is an emergency call 911", counsel.]
- Intake must not fail silently (16.6): two independent paths per form lead (Worker's direct email + n8n); n8n error workflow; staleness rule (continuity alert); repeat-safe writes (dedupe key); manual fallback (plain email + phone printed in onboarding sheet); 10-second wait before looped Sheets writes; no secret in workflow export. n8n is prototype-grade for mission-critical intake (course CTO's warning).
- Ledger (16.7, E.1): start on sheet + n8n + alerts, client-owned, shared to NAMED accounts only (never link). Columns: id, received_at, type, source, campaign_or_page, contact (phone E.164), service, location_or_zip, message, answered, first_contact_at, minutes_to_contact, duration_s, recording_url, tag (lead/marketing/junk), qualified, status (new, contacted, estimate-booked, estimate-given, won, lost, out-of-area, spam), job_value, heard_via, consent_sms, consent_ts, is_test, notified_at, notify_error. Formula-injection fix: write cells RAW or prefix `'` for values starting `=+-@` (REVIEW-3 M9, REVIEW-4 L9). [M: a ledger holding patient names + reason-for-visit is PHI; counsel/BAA; REMOVE message/clinical fields.]
- Friday text (E.2, 16.8): "[N] calls, [A] answered, [L] real leads, [M] marketing/junk, [X] missed", three tiers (standard / high missed rate / high spam rate / strong week). Monthly tag review: client confirms qualified/booked/won/revenue. Disputes: keep tagged call log.
- Route only to a real, named, licensed business that knows it receives the lead (16.9). [T: microsite model.]

Hero media = one static REAL photo < 150 KB eager-loaded (static beat animated heroes/carousels in coach split tests - practitioner).

### 1.11 Forms: field and UX rules (10.7, U08) [X]
- Fields: name, phone (the KEY field), what you need (short select of REAL services), ZIP/address, optional email, optional message. Form-length evidence is vendor-sourced and mixed (one case with fewer fields lost 14%); 2-step defensible; TEST, don't assume.
- U08.5 minimum fields only; each extra field needs a stated use. U08.6 visible labels (never placeholder-only), validate on submit not on blur. U08.7 mark "(optional)", no asterisk. U08.8 failed submit: error summary above H1 headed "There is a problem", links to each field, focus moves to it, page title starts "Error:". U08.9 long forms one thing per page; anything with legal/financial commitment gets a review step. U08.10 confirmation page: what happened, reference number, what next and when, contact route; event fires there. U08.11 fail closed. U08.12 two destinations. U08.14 link-test every CTA (generated sites ship dead buttons: `action="#"`, `preventDefault`-only forms, `mailto:` actions, `/#contact` anchors that don't exist; headless click-through at 390 and 1280 px). U08.15 no pre-checked boxes. U08.19 third-party embeds tested by keyboard/phone with a fallback link/phone.
- Consent line with its own checkbox if data will feed a text or callback ("I agree to be contacted by call or text, including by automated technology").
- Thank-you page: what happens next and when; phone for urgent; <100 words; fires the conversion event once; never a fake "thanks" without delivery.
- Turnstile script ONLY on pages with a form; never put a bot wall in front of the whole site (hides site from crawlers/tools; 3 of 13 NYC competitor sites were un-fetchable).

### 1.12 What changes for a MEDICAL practice [MED-NEW unless sourced to R14 2.4 / medical-wellness overlay]
Sourced (R14 2.4, overlay medical-wellness, draft, counsel flags):
- Primary conversion: appointment request/booking or call; existing patients need a SEPARATE portal link kept apart from the new-patient path.
- Request form collects SCHEDULING details only, never symptoms or history, unless the form vendor signs a BAA and counsel approves (overlay "Primary conversion", U08, U21).
- No ad/social pixels or session replay on appointment, portal, condition or provider-search pages; analytics there cookieless, counsel approves setup (overlay medical-wellness.4, overrides U19.8). HHS OCR tracking bulletin (Dec 2022) partly vacated 20 Jun 2024 (AHA v. Becerra: IP + public unauthenticated page visit not PHI); remains: authenticated pages/portals may involve PHI, vendors need a BAA, a cookie banner is not a HIPAA authorization.
- Trust: provider credentials checked against the issuing board's public lookup; current dated list of accepted insurance (front desk confirms at each content review); real reviews with replies that NEVER confirm the reviewer is a patient and disclose no patient info.
- Legal pages (counsel): notice of privacy practices (45 CFR 164.520 website posting duty - R14 said NOT verified; overlay cites Cornell LII as B-grade); good-faith-estimate notice for uninsured/self-pay (45 CFR 149.610) prominently on site and findable by search; nondiscrimination/language-assistance where applicable; accessibility statement. FTC Health Breach Notification Rule (16 CFR 318) for non-HIPAA health services. HHS Section 504 web rule (WCAG 2.1 AA; 15+ employees deadline 2027-05-11; small-entity date conflicting 2027/2028; only if HHS-funded).
- Health claims: provider reviews and evidence backs every claim (FTC Health Products guidance via law-firm summaries); no "top doctor"/"best clinic"; no before-after photos without written patient consent and counsel approval; no health blog without clinical review.
- State medical/dental board advertising rules: NOT researched. Counsel.
- Schema: `MedicalClinic`/`Dentist`/`Physician`; `Person` per provider with `hasCredential` only for board-verified credentials; insurance plans only from record with `as_of` date.
- Common medical mistakes (overlay): pixels on appointment/portal pages, unverifiable "top doctor", before-after without consent, stale insurance lists, booking forms that ask symptoms, review replies confirming treatment.
- Open counsel questions already listed in overlay: tracking on which pages/which vendors need a BAA; Section 504 date; state board rules/state health-data laws; testimonial/before-after consent; nondiscrimination notices. Pending NY Health Information Privacy Act (S9269/A10357, vetoed Dec 2025, revised bill pending) could reach trackers on health sites (R5 7.4).

Inferred additions for the conversion stack (not in sources): (a) keep message field out of alert emails/SMS/Sheets (or use secure portal link); (b) phone is the highest-intent path for many patients but never promise a clinical answer by text; (c) no call recording by default; (d) booking embed vendors = BAA question + ADA accessibility question (booking overlay open questions); (e) form `service` select = specialties/visit types; use ZIP optional; (f) sticky call bar fine but "emergency strip" must say "If this is a medical emergency call 911" and only show real answered hours; (g) the 5-min callback target applies to appointment requests during office hours; after-hours = clear next-business-day expectation; (h) language access matters in NYC (see H.10).

## 2. EDGE-CASE REGISTER (Appendix H, with IDs and handling rules)

Global rules (H preamble): (1) dated snapshot before any change; (2) one change at a time, logged; (3) never promise recovery or a date. Each case in source has: recognise / risk / handling / tell client / evidence / confidence / unverified. Confidence H = Google's own text; M = primary + inference; L = single/opinion. Condensed below. Applicability to a medical practice: Y = applies as written, M = adapt, T = trades-only.

### H.1 Multi-location (2+ branches/yards) [M]
Recognise: two numbers/license counties, "yard + office". Risk: duplicate profile hidden from Search/Maps; doorway pages; shared tracking pool hides which branch earns; reviews can't move between listings.
Handling: (1) profile count by Google's rule: service-area business, no storefront = ONE profile; separate locations each get one only with own service areas AND own staff; service area ~2 hours' drive. (2) qualifying branch: same business name (unless real-world name varies), same primary category for same service, own verified phone, own landing page; unstaffed location = no profile, no address shown. (3) one domain; locations hub only when 2+ qualify; a branch page needs facts no other page has (address, crews/hours, licence for that county, local jobs w/ photos, local reviews, branch phone) else fold into area system; no find-and-replace city pages. (4) schema: one `LocalBusiness` (most specific subtype) per qualifying location, own `@id`, `url`, `telephone`, `openingHoursSpecification`; never mark up hidden address. (5) one tracking pool per branch + branch hidden field on forms + ledger + report column; real line primary, tracking secondary. (6) separate review link per profile; never copy reviews between pages/schema or steer to another branch. (7) one service page per service with short coverage block; don't clone per branch. (8) one primary owner per profile = the client. Tell client: "A second listing only for a branch with its own staff and service area; a non-qualifying one can hide both." Confidence H on eligibility, M on structure. Unverified: two profiles sharing one address and staff.
[MED: very relevant for multi-office practices and for providers who work at several sites; per-provider location pages need real hours/staff.]

### H.2 Prior penalty or history [Y]
Recognise (at qualification 4.2): GBP Suspended/Verification needed/Not published; second pin or "closed" twin; GBP name differs from signage/licence/insurance; Search Console (get owner access): Manual actions, Security issues, 16-month Performance vs update dates; Wayback history; spam links/injected pages (view-source, `site:`).
Handling: (1) classify (H.4 step 3). (2) GBP suspended: do NOT create a new profile; use appeals tool, one appeal per decision, documents whose name/address match the profile (registration, licence, tax certificate, utility bill); no name/address/category edits during appeal; build evidence pack first (17.9). (3) Duplicate/merged: merge via Maps "Suggest an edit" (reviews combine, replies may be lost); removing your own duplicate deletes its content and managers; survivor = by verification and review history (ours). (4) keyword-stuffed name: options (a) leave + document risk + build the rest; (b) once stable, change to real-world name in ONE edit, expecting re-verification/rank move (17.6). Never copy a competitor's stuffed name. (5) manual action: fix ALL affected pages, ensure Googlebot access, Request Review explaining problem/fixes/results; don't resubmit while pending; unnatural links: remove/nofollow, disavow rest, document. (6) security issue: clean + patch cause, test, then Request Review (asking early can lengthen next turnaround). (7) core-update fall: no fix -> H.4. (8) toxic links/spammy history: audit; consider fresh domain (4.6) = a site move (H.3). (9) log history; add audit hours to quote; promise no date. Timing: SC "several days to weeks"; GBP appeal duration unsourced.

### H.3 Migration off existing WordPress site [Y if client has WP]
Risk: Google expects ranking to "fluctuate" a few weeks+; the 70% loss is one practitioner claim (R2 J1/K0067); breakages: redirect map misses real URLs, form history lost, ranking images vanish, Search Console/analytics verification lost, email stops when DNS replaced, staging `noindex` left on, capture broken at cutover.
Handling: 1 access to WP admin, host, registrar, DNS, Search Console (owner), analytics, form recipients, email host; full backup (files+DB), read-only; freeze plugin updates. 2 crawl live site (title, meta, H1, canonical, noindex, schema, status, images, PDFs, inlinks) + URLs a crawl misses (sitemap, Search Console Pages/16-month Performance, Links report, analytics landing pages, server logs, WXR slugs/post IDs). 3 baseline: 12 months clicks, calls, forms by source; ## 3. PER-PAGE SPECS (7.2, 12.3, 6.x, 10.x) [X unless flagged]

### 3.1 Site planning rules
- Archetype first (6.1): SAB / storefront / hybrid / multi-location. Medical = usually storefront (shown address, `address`+`geo`) or multi-location (one node per location, own `@id`).
- Page plan sheet `plan/pages.md` (6.10): URL | page type | primary keyword | title | source of proof | word target | tier | status. Owner approves before build. One keyword per URL. No page exists that isn't on the plan (22.2).
- Tiers (6.3): Launch set ~13-16 pages counting utility pages (REVIEW-2 #9: the 6.3 arithmetic said "10-12" but list sums to 13-16): Home; 2-3 category/core service pages; 3-5 service pages; one consolidated area page; About; Contact; thank-you; privacy and terms; 404. Growth set ~20-25 months 2-4 (FAQ/facts page, gallery/projects, rest of services). Full "Core 30" ~30-40 pages months 4-9, mirrors the GBP one-to-one. Order: category -> services -> locations (check rank at 3-4 weeks). Q-005: every service on the site exists on the listing, AND listing lists only services that have launched.
- Titles (6.6): primary category + city first, brand last, ~60 chars; H1 differs from title; home title `[Primary category] + [City]`; generate copyright year from build date.
- URLs (6.5): under 50 pages short top-level slugs; over 50 nest `/services/{slug}/`, `/areas/{slug}/`; never service-by-place slug (`/roof-repair-queens/`) which is a templated page (C1). Route collision: use `/services/[slug]`, `/areas/[slug]`, add `categories` (REVIEW-2 #22).
- Area pages (6.4): ONE consolidated page per area, never per landmark (C1); 1,000-1,500 unique words; >= 80% of entity checklist (named neighborhoods, landmarks, text driving directions, one local reference, one local price/timing fact); testimonials from that area (omit if none - don't invent; REVIEW-2 #9: then judge on other checks); captioned photos; embedded map; 4-6 logistics FAQs; 1 outbound link per 1,000 words. Clone test: `site:theirdomain.com /area-path`. NYC: neighborhood pages only for names Google Maps shows; rank collapses at the city line (practitioner).
